# AIMES Token 效率设计与优化建议

- 日期：2026-10-18
- 状态：纳入 P0—P3 验证前的设计补充；运行时效果待基准测试
- 适用范围：AIMES Core、项目规则入口、Skills、Context Pack、任务交接、CLI 报告与 CI
- 核心目标：以更少的输入/输出 Token、重复检索和模型调用，维持或提升工程正确性、可追溯性与安全性

## 1. 结论

AIMES 已在提示词系统契约中提出“上下文预算”和“最小充分上下文”，也已有 Skill 编排、Context Pack、任务交接和结构化校验等基础。因此不应另造一套平行的 Token 治理体系，而应把既有原则变成可执行的加载策略、预算、指标和评测。

当前最值得补齐的不是单纯压缩核心规范，而是：

1. 将“入口规则 → 任务相关材料 → 未决问题定向扩展”变成默认执行路径。
2. 区分必须常驻的硬规则与按任务加载的专业知识，避免每次加载全部 Core、全部 Skills、全部项目文档。
3. 将 Context Pack 从“文件清单与哈希”逐步升级为可控的任务上下文索引/摘要；原始文件仍是事实源，摘要必须可追溯且不得取代原文。
4. 用基准任务测量 Token、调用次数、完成时间、返工率和硬门禁退化，防止为了省 Token 损害质量。
5. 对重复报告和多份相互重述的说明建立单一权威来源，其余文档只提供简短摘要和链接。

## 2. 已有基础与差距

| 领域 | 已有基础 | 当前差距 |
|---|---|---|
| Core 与入口 | 单一治理核心、薄入口 | 需要明确哪些规则必须始终加载，哪些按需加载；不能假设“引用文件”即等于模型已读取 |
| Prompt/Skill | `PROMPT-SYSTEM-CONTRACT-V1.0.md` 第 7 节已有上下文预算；编排协议允许按条件跳过 Skill | 缺少可执行的预算配置、选择日志和质量/成本联合基准 |
| Context Pack | `context pack` 记录任务、实体、上下文文件路径、SHA-256，并生成 HANDOFF | 当前主要记录文件清单/哈希，不会自动抽取任务相关片段，也不统计估算 Token；需避免生成过长的重复摘要 |
| CLI 与报告 | 有结构化报告、证据校验和工程指标框架 | 尚无可验证的 Token 使用数据源；工程质量指标不能直接代表 Token 效率 |
| 文档体系 | Core、README、命令契约、技术设计和优化报告各有用途 | 部分命令/能力说明有重复，需明确“权威详情在一处，其他位置只做导航” |

## 3. 规则加载分层

### L0：每次任务必须提供的最小护栏

保留短小、稳定、不可按预算裁剪的内容：

- 权威事实源和冲突处理优先级；
- 用户修改保护、写权限/审批和破坏性操作边界；
- 状态不得伪造，VERIFIED 必须有证据；
- 任务范围、基线与 Git 状态核验；
- 验证要求、未知/阻塞披露和交接落盘；
- 如何查找项目配置、任务状态与权威文档。

建议工具入口只放 L0 摘要及 Core 链接。若工具无法自动读取链接目标，启动模板必须明确要求读取哪些具体文件并回报实际路径。

### L1：按任务选择的专业规则

仅在触发条件满足时加载：

- 需求分析/需求变更：需求认知 Skill、相关需求和验收标准；
- Bug 修复：相关代码、失败测试、对应需求和最近变更；
- 架构/公共接口变更：架构契约审查、相关 ADR 和接口契约；
- 测试设计：测试策略、需求验收、相关测试工具/数据规范；
- 发布/依赖升级：发布流程、兼容性矩阵、构建和回滚说明；
- 清理/归档：资产引用、保护清单、清理规则。

### L2：基于证据的定向扩展

只有当现有材料不足、出现冲突、影响范围扩大或验证失败时，才读取更多文件、调用更多 Skills 或扩大检索范围。每次扩展要说明它要解决的具体未知问题；不得因为“可能有用”而无边界地扫描整个仓库。

### 不能为了省 Token 跳过的硬门禁

- 用户修改/工作区状态检查；
- 高影响需求与批准状态核验；
- 安全、数据、权限、公共契约等风险检查；
- 真实测试与证据要求；
- 合并/发布前的集成验证。

预算耗尽时应缩小非关键探索、分阶段处理或请求用户决策，不得静默跳过硬门禁或把 UNKNOWN 改为 PASS。

## 4. Context Pack 与交接优化

1. 默认生成精简索引：任务目标、基线 commit、受影响实体、关键路径、验证状态、未决问题和下一步。
2. 文件只列出“为什么相关、应读哪一段、源文件哈希/基线”；不要把大文件全文复制到 Context Pack。
3. 可选增加按章节/符号的片段引用，但必须保留源路径和定位信息；摘要只用于导航，不作为需求、代码或证据的权威替代。
4. 对已验证且基线未变化的结果，优先引用证据 ID/报告路径，不重复粘贴完整日志；基线变化时标记为需复核。
5. 区分“估算 Token”与“实际 Token”：没有对应模型/工具的真实计量数据时，只报告字节数、字符数或估算值，并明确其不是实际计费 Token。
6. 交接报告采用固定短模板；详细分析保存在任务文件或报告中，由交接索引链接，不重复整份分析。

## 5. 文档去重与单一事实源

- Core：只定义跨项目必须遵循的规则。
- 项目配置：只定义项目路径、工具、测试命令、门禁和例外。
- Skill：只包含特定任务的步骤、决策与输出契约。
- 命令契约：只定义 CLI 参数、输出和退出码；README 提供最常用示例并链接完整契约。
- 实施报告：记录本次变更、证据和未验证边界；不复制整段规范。
- 交接：只记录当前任务增量，不重述完整项目背景。

检查重复内容时优先合并权威定义并替换副本为链接；不要为减少行数而删除必要的安全解释、反例或证据边界。

## 6. 提示词优化的能力非退化约束

本设计明确禁止把大幅压缩提示词作为默认的 Token 优化手段。提示词的长度本身不是质量指标；其中可能承载必要的领域知识、约束、执行步骤、反例、异常分支和验收条件。

### 6.1 允许优先优化的内容

1. 相同规则被多个入口、Skill、任务上下文或交接报告重复注入。
2. 与当前任务无关、且不满足触发条件的专业材料被加载。
3. 同一文件、日志、分析结论或验证证据被反复读取/粘贴。
4. 缺乏明确目的的仓库扫描、重复模型调用和过度展开的报告。
5. 可以通过稳定索引和精确定位获取、且目标工具确实支持按需读取的内容。

### 6.2 不得为了省 Token 而删除或弱化的内容

- 业务语义、用户意图、需求约束、非目标与验收标准；
- 专业方法、必要的执行步骤、决策条件、关键示例和反例；
- 安全、权限、用户修改保护、失败处理、回滚和升级路径；
- 必需的验证步骤、证据标准、状态定义和结果披露；
- 会影响输出完整性、兼容性、可维护性或风险控制的边界说明。

内容确实重复时可以合并，但必须保留所有独立语义；如果无法证明两段内容等价，按非重复内容处理，不得直接删除。

### 6.3 提示词重构的验收门槛

任何 Core、Skill、规则入口或工作流提示词的精简/重构，都必须：

1. 记录变更前后的行为意图、被合并的语义及其权威来源；
2. 在相同代表性任务、相同环境和相同验收标准下进行对照；
3. 检查需求覆盖、边界遵循、结果完整性、异常处理、测试质量、返工和完成时间；
4. 确认硬门禁失败数不增加，工程质量达到预先定义的非劣标准；
5. 对未实际执行的评测标记 NOT_RUN / UNKNOWN，不得宣称能力等价；
6. 若能力退化或遗漏增加，恢复必要内容或撤销精简，即使 Token 数因此上升。

**优化成功的判据是“能力不退化且总体成本下降”，不是“提示词更短”。** 在没有完成等效性评测前，提示词压缩只能作为待验证提案。

## 7. Token 效率的衡量

建议为固定基准任务记录以下指标：

| 指标 | 定义 | 数据来源/限制 |
|---|---|---|
| 输入 Token | 任务实际消耗的输入 Token | 仅使用工具/模型真实 usage；无数据则 UNKNOWN |
| 输出 Token | 任务实际消耗的输出 Token | 同上 |
| 总 Token | 输入与输出之和；缓存 Token 可另列 | 不能把字符数直接称为实际 Token |
| 模型调用数 | 完成任务的模型请求次数 | 工具/平台运行记录 |
| 上下文加载量 | 实际提供给模型的文件/片段与大小 | Context Pack/工具记录；估算值需标记 |
| 首次通过率 | 首轮交付通过独立验收的任务占比 | 固定验收标准与基准任务 |
| 返工率 | 因遗漏上下文、误解或回归导致重做的任务占比 | 任务/缺陷记录 |
| 硬门禁退化数 | 相比基线新增的安全、测试、追溯或证据失败 | 独立门禁结果 |
| 任务完成时间 | 从开始到验收完成的时间 | 任务记录；需统一起止定义 |

不得以“Token 越少越好”单指标优化。推荐采用约束式目标：**硬门禁不退化、首次通过率不下降的前提下，降低总 Token、模型调用和返工成本。**

## 7.1 固定基准与执行入口

基准任务、A/B 对照方法、质量非退化门槛和运行记录字段以 [TOKEN-EFFICIENCY-BENCHMARK-PLAN-2026-10-18.md](TOKEN-EFFICIENCY-BENCHMARK-PLAN-2026-10-18.md) 为准；固定的 8 类评测案例位于 [token-efficiency-suite.yaml](../../examples/evaluation/token-efficiency-suite.yaml)。通过 `aimes evaluation validate` 仅证明案例结构符合契约，不代表模型已运行或能力已通过验证。执行状态在真实运行前必须保持 `NOT_RUN`，实际 Token 不可得时记为 `UNKNOWN`。

## 7. 推荐实施顺序

### T0：先定规则（本次验证前）

- 将 Token 效率写入 Core 原则与提示词系统契约。
- 采用 L0/L1/L2 加载分层和硬门禁不可裁剪原则。
- 明确实际 Token 与估算 Token 的区别。
- 文档中声明：Context Pack 当前不自动提取代码片段或测量实际 Token。

### T1：建立基准（规则加载验收时同步）

- 选取 5—10 个代表性任务：简单问答、小 Bug、常规功能、架构变更、测试设计、跨工具交接。
- 为每个任务固定初始 commit、需求、验收标准和硬门禁。
- 对比现有全量/人工加载方式与最小充分上下文方式。
- 记录质量、Token（可获取时）、调用数、返工和完成时间。

### T2：轻量自动化

- 为 Context Pack 增加可选的预算配置、文件/章节优先级、最大文件数/字节数和截断说明。
- 报告显示“纳入/排除材料及原因”，不静默截断关键安全/验收材料。
- 支持按任务生成精简 HANDOFF 和上下文清单；保留手工指定文件的兼容性。
- 增加 `aimes context validate` 对预算配置、源文件哈希和遗漏必需项的检查。

### T3：基于真实使用持续优化

- 只有在模型/工具可提供真实 usage 时才汇总实际 Token。
- 对低成本方案做质量非劣性评估；失败案例回补基准集。
- 只优化重复加载、无关检索和冗长输出，不削弱证据、授权与安全规则。

## 8. 验收标准

- [ ] Core 与 Prompt Contract 有明确的 Token 效率原则和分层加载策略。
- [ ] 入口文件保持薄，不复制完整规则正文。
- [ ] 硬门禁被明确列为不可因预算而跳过。
- [ ] Context Pack 对实际功能与边界描述准确，不宣称已实现自动 Token 计量/语义检索。
- [ ] 基准任务同时比较工程质量与成本；缺失 usage 数据标为 UNKNOWN。
- [ ] 低 Token 方案不得增加硬门禁失败、未经批准写入或虚假 VERIFIED。
- [ ] 实际 Token 优化效果必须由真实工具运行记录证明，静态文档检查不能代替。

## 9. 本轮结论

本次先将 Token 效率纳入治理规范和设计基线，不在缺少运行时 usage 数据与基准结果时宣称节省了某个百分比。后续优先对 Context Pack 与 Skill 加载流程做小步增强，并用固定任务集验证“更少 Token、质量不退化”。

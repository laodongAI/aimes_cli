# AIMES 治理能力升级：P0 现状审计

- 审计日期：2026-10-18
- 审计范围：GitHub `laodongAI/aimes_cli` 的 `main` 分支公开文件
- 审计方式：README、命令契约、工具适配矩阵、验收计划、技术设计基线及关键 Python 模块静态审阅
- 证据边界：本报告是源码/文档静态审计；本轮未在 Windows 本机、AI Native 测试系统工作区或真实 IDE 会话中执行测试，因此不把静态审阅描述为运行时验收。

## 1. 总体结论

AIMES 已经不是只有治理规范的原型：仓库包含配置初始化、适配器记录、需求/知识/复用/Skill 契约校验、追溯与证据校验、Context Pack、评测记录与回归比较、结构化审计和 GitHub 发布等能力。

因此，P1 不应重写已有检查器，而应补齐现有能力之间的缺口，并把检查器纳入可重复的统一治理流程。

当前最关键的缺口是：
1. 真实工具的规则加载仍缺少可复核的运行时验收记录。
2. 文档结构/链接与薄入口漂移检查尚未在当前 CLI 命令契约中形成明确的可执行命令。
3. 任务级协作状态（活动写入者、任务文件范围、租约/交接状态）尚未形成完整 CLI 协议。
4. 临时产物注册与清理审计仍是设计目标，不应误报为已实现。
5. 文档版本和实现版本存在可见漂移。

## 2. 已确认事实

### 2.1 已有实现（静态源码可见）

- `src/aimes_cli/cli.py` 注册了 `trace validate`、`evidence validate`、`context pack/validate`、`adapter validate/report`、`evaluation validate/report/compare/run-mock`、`audit append/validate` 等命令。
- `src/aimes_cli/v03.py` 中存在追溯实体、链接、VERIFIED 证据引用、证据文件和上下文路径校验逻辑。
- `src/aimes_cli/v05.py` 中存在工具验证记录、证据文件/哈希、Context Pack 源文件哈希检查。
- `src/aimes_cli/validators.py` 中存在 requirement、knowledge、reuse、skill 的结构化契约校验。
- `src/aimes_cli/core.py` 中存在项目初始化、入口模板、manifest 和项目配置校验相关逻辑。
- `docs/TOOL-ADAPTER-MATRIX.md` 明确区分 UNKNOWN、TEMPLATE、STATIC-PASS、RUNTIME-PASS、LIMITED，且规定不能把 TEMPLATE 自动升级为 RUNTIME-PASS。
- `docs/ACCEPTANCE-TEST-PLAN.md` 明确将真实工具验收列为待执行事项，并规定实测完成前应保留 MVP/STATIC TESTED/RUNTIME NOT VERIFIED 的状态。

### 2.2 版本和文档漂移

- `pyproject.toml` 的包版本为 `0.7.7`。
- `src/aimes_cli/__init__.py` 的 `__version__` 为 `0.7.7`。
- `README.md` 标题和多个章节仍标注 `V0.7.4`。

这属于可直接确认的文档版本不一致，应在版本发布流程中统一维护，不能仅靠人工记忆。

### 2.3 设计文档与当前实现边界不一致

`docs/TECHNICAL-DESIGN-BASELINE.md` 将 docs check、任务创建/交接、清理审计等描述为目标命令或待建设能力；当前 `src/aimes_cli/cli.py` 的命令注册中没有独立的 `docs check`、`task` 或 `cleanup audit` 命令。

这不代表技术设计文档错误——它可能是历史设计基线；但需要标明哪些条目已实现、部分实现、尚未实现，并链接到实际命令，避免读者将设计目标误认为现有功能。

## 4. P1 实施约束

1. 优先复用已有模块和 JSON 报告约定，不另造重复的追溯/证据模型。
2. 所有新检查默认只读，不自动修改项目规则或删除文件。
3. 检查器区分 ERROR、WARNING、NOT_RUN 和 UNKNOWN；不能将缺少证据解释为通过。
4. 新功能必须包含单元测试、正反例 fixture、退出码测试和 JSON 输出测试。
5. 先以独立 CLI 命令验证，再接入 CI；历史遗留问题采用基线策略，防止一次性阻断正常开发。
6. 真实 IDE 规则加载必须由运行时证据证明，静态文件检查不能替代。

## 5. 本轮未验证事项

以下内容需在本地/目标环境执行后才能判定：
- Python 测试套件当前是否全部通过。
- Windows 安装包/EXE 是否与源码版本一致。
- 所有工具的当前产品版本、规则入口和实际加载行为。
- AIMES 在 AI Native 测试系统中的真实配置、追溯资产、CI 与工作区状态。
- 历史文档、示例、Schema 与所有实际代码路径的完整一致性。

## 6. 建议的后续执行顺序

1. 完成目标工具运行时验收记录；在验收前维持 UNKNOWN/NOT_RUN。
2. 修复版本标注漂移，并建立发布版本一致性检查。
3. 实现薄入口漂移检查与 docs check。
4. 明确配置化追溯注册表和现有 trace validator 的边界。
5. 再进入活动写入者、任务级交接、讨论模板和临时产物治理。
6. 最后统一指标口径、采集与持续改进报告。

# AIMES 工程能力增强路线图 V0.9

## 1. 目标

AIMES 的目标不是单纯安装规则和 Skills，而是帮助 Codex、Claude Code 等 AI 开发工具更可靠地完成需求分析、设计、开发、测试、代码与文档规范、版本管理和 Token 优化。

下一阶段的核心转变是：从“配置已生成”转向“行为已验证、质量可比较、改进可复现”。

## 2. 八个工作流

| 工作流 | 优先级 | 本阶段目标 | 完成证据 |
|---|---|---|---|
| W1 版本事实源与发布治理 | P0 | 统一包版本来源；校验运行版本、README、治理核心和发布元数据；清理历史文档误导 | CI 版本校验通过、发布清单可追溯、安装说明无旧版本硬编码 |
| W2 AI 工具运行时验证 | P0 | 将文件存在、规则加载、行为遵循、工程结果、效果收益分层 | 每个目标工具/版本/执行模式有独立证据记录 |
| W3 Skill 契约与生命周期 | P0 | 统一输入/输出、权限、停止条件、失败恢复、验收和版本字段 | Skill Schema 校验与代表性任务评测 |
| W4 工作流编排 | P1 | 定义可恢复状态机、分支、审批、幂等和交接 | 正常/失败/中断恢复案例通过 |
| W5 AI 工程质量评测 | P1 | 建立基线、候选、留出集和独立验收 | 相同任务集的对照报告，硬门禁不退化 |
| W6 上下文与 Token 优化 | P1 | 记录实际读取范围、usage、重试、返工和任务质量 | 真实 usage 数据及质量非退化报告 |
| W7 插件化适配器 | P1 | 适配器声明执行模式、能力、入口、权限、版本和验证配置 | 新增工具不修改治理核心；适配器契约测试通过 |
| W8 安全与产品体验 | P1/P2 | 加强路径边界、权限分级、事务日志和简单/高级操作模式 | 安全负向测试、异常恢复测试和可用性试点 |

## 3. 实施顺序

### 阶段 A：可信基线（当前阶段）

- [x] 明确自动化测试不等于运行时验证的状态语义。
- [x] 建立能力与验证状态矩阵。
- [x] 将 Python 包版本配置改为从 `aimes_cli.__version__` 动态读取，避免包元数据和运行版本各自维护。
- [x] 扩展发布校验测试，覆盖动态版本来源及不合法配置（GitHub Actions 单元测试已通过）。
- [x] 归档 V0.5.3 旧构建/测试报告与哈希清单，并让发布校验阻止历史制品重新出现在仓库根目录。
- [x] 修复 README 的历史 wheel 安装路径，改为源码安装流程并链接能力矩阵与路线图。
- [ ] 校验 CHANGELOG 当前版本、README 安装步骤和发布产物元数据。
- [ ] 对照 GitHub Actions 运行结果核验主干测试、Windows EXE 构建和冒烟检查。
- [ ] 生成当前版本发布清单并确认正式 Release/tag/资产状态。

**阶段 A 验收：** 版本事实一致；版本校验可阻断不一致；安装文档可执行；所有发布声明有对应 CI 或 Release 证据。

### 阶段 B：真实工具试点

首批只选 Codex CLI 与 Claude Code CLI，先避免一次性铺开八种上下文。

- 固定至少一组真实项目需求分析、实现、测试和交接任务。
- 每组任务记录工具版本、模型版本、AIMES/治理/Skill 版本、仓库基线和验收标准。
- 先运行基线配置，再只改变一个规则/Skill/上下文因素运行候选版本。
- 由测试、静态检查或独立评审验收，不把模型自评作为唯一证据。
- 记录真实 Token usage；不可获取时使用 UNKNOWN，不估算替代。

**阶段 B 验收：** 每种试点工具都有可复核运行记录；报告区分加载、遵循、结果和收益；至少包含失败案例及已知局限。

### 阶段 C：Skill 契约与工作流引擎

- 将 Skill 输入、输出、权限、完成判据、停止条件和失败恢复结构化。
- 将工作流状态与任务产物持久化，支持中断恢复、幂等重试和人工审批。
- 为每个工作流状态定义进入条件、产物、成功条件、失败分支和可恢复策略。
- 仅在已有真实试点证明收益后，自动化高频且低风险的步骤。

**阶段 C 验收：** 状态机测试覆盖正常、失败、取消、中断恢复和重复执行；关键步骤可审计。

### 阶段 D：扩展适配与用户体验

- 使用声明式适配器清单描述工具能力和执行模式。
- 将适配器验证记录纳入兼容性报告。
- 提供简单模式和高级模式；先完善 CLI 的向导与报告，再评估 GUI。
- 对路径越界、提示注入、未经授权写入、敏感信息和失败回滚进行负向测试。

## 4. 设计原则

1. **证据优先**：状态只由对应证据支持，不因文档声明自动晋级。
2. **最小改动**：先改版本和验证闭环，不在第一阶段重写整个 CLI。
3. **兼容优先**：现有命令和项目配置默认向后兼容；不自动删除用户文件。
4. **可恢复**：所有有副作用的操作先预览，写入有备份/日志，失败有明确恢复指引。
5. **模型无关**：核心契约不绑定单一模型或 IDE，工具差异留在适配器层。
6. **质量优先于 Token**：任何关键质量门禁退化都使优化失败。
7. **明确未知**：未运行、不可观测或证据不足必须记录 UNKNOWN/NOT_RUN/BLOCKED。

## 5. 发布和验收门禁

- 单元测试与静态校验通过。
- `aimes release validate --root .` 通过。
- Token 评测集结构校验通过。
- Windows EXE 在 CI 中构建并完成冒烟测试；发布包需要独立核验版本和文件完整性。
- 真实工具验证状态不得从 UNKNOWN 自动提升。
- Release notes 明确说明已实现、已验证和未验证的边界。

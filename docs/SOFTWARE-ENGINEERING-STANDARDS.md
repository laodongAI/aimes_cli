# AIMES 软件工程需求、设计与开发规范

状态：PROPOSED（AIMES 通用基线；项目批准规范优先）
版本：1.0.0

## 1. 目标

将需求质量、技术设计质量和代码实现质量纳入统一工程治理。规范不要求所有项目采用相同技术栈，而是要求每次变更具备明确目标、可审查设计、合理模块边界、复用决策、可验证实现和可追溯交付。

## 2. 端到端质量门禁

| 阶段 | 必须回答 | 核心产物 | 未通过时 |
|---|---|---|---|
| 需求 | 为谁解决什么问题？边界和验收是什么？ | 需求记录、用户流程、验收标准、开放问题 | 阻断级歧义暂停受影响实现 |
| 设计 | 放在哪个模块？职责、接口、数据、状态和依赖是什么？ | 设计说明、模块/组件图、API/数据契约、ADR（适用时） | 架构冲突或破坏性契约等待批准 |
| 开发 | 是否复用已有能力？代码职责是否清楚？ | 实现计划、复用清单、变更 Diff、测试 | 越界/用户改动保护失败即停止 |
| 验证 | 如何证明行为正确、边界可靠？ | 测试矩阵、命令/退出码、测试报告 | 失败保留证据；未运行不得报通过 |
| 交付 | 需求、设计、代码、测试和文档是否一致？ | 追溯映射、交付报告、剩余风险 | 缺项显式标记，不得虚报 VERIFIED |

典型 Skill 链：requirement-cognition → project-knowledge-reuse → change-impact-analysis → architecture-contract-review（适用时）→ software-engineering-standards → controlled-implementation → requirement-driven-testing。Vue 任务再调用 vue-frontend-engineering；涉及视觉体验时调用 UI Skills。

## 3. 需求规范

- 需求说明用户/角色、场景、目标、业务价值、前置条件、主流程、异常流程、权限、数据边界和明确不做事项。
- 每条需求应可追溯，使用稳定 ID；区分已批准、候选、假设、未知和冲突。
- 验收标准应可观察、可判定，优先采用 Given/When/Then 或等价结构。
- 覆盖正常、负向、边界、异常、权限、并发/重复请求、性能/可用性（适用时）。
- 不把技术实现方式写成业务需求；不把模型推断当作用户批准。
- 变更需求记录原因、影响范围、兼容性、受影响验收标准和审批状态。
- 阻断级歧义先澄清；非阻断细节可形成明确假设，记录影响和验证方法。

## 4. 技术设计规范

中大型功能至少说明目标/非目标、约束/风险、现有模块和复用情况、模块职责/边界/依赖方向/数据所有权、关键流程/状态机/异常分支、API/事件/数据模型及错误语义、权限/安全/审计/信任边界、性能/并发/缓存/幂等/超时/重试/恢复策略、测试策略、迁移兼容、回滚和文档影响。

设计原则：
- 优先沿用项目架构和稳定模式，不为套用模式增加无意义层级。
- 模块高内聚、低耦合、单向依赖；避免循环依赖和跨层访问。
- 公共接口/组件/数据结构先定义契约，再实现。
- 破坏性 API/数据变更说明版本兼容、迁移窗口和回滚。
- 复杂决策写 ADR；局部实现细节写模块设计；临时分析不冒充批准设计。

## 5. 开发实现通用规范

### 5.1 复用优先
编码前检索已有页面、组件、Composable/Hook、Store、API client、服务、Repository、类型、校验器、工具函数和测试。输出复用清单：复用、组合、扩展、新建或不复用及原因。相似代码并不必然语义相同；抽象基于共同职责、稳定契约和变化原因，避免复制粘贴和过早万能框架。

### 5.2 模块职责
页面/控制器/路由层负责协议和流程入口，不承载所有业务规则；应用服务负责用例编排，领域层承载稳定业务规则；数据访问和外部服务通过明确接口/适配器隔离；公共组件/服务不得反向依赖具体页面或调用方内部状态；副作用显式化，关键操作定义错误、超时、取消、幂等和恢复。

### 5.3 可维护性与安全
函数、类、组件单一职责；命名表达业务意图；避免巨型文件、长函数、深层嵌套、重复分支、隐式全局状态和过度参数。关键输入输出有明确类型和校验；禁止滥用 any、无约束字典和不安全转换。统一异常语义，禁止吞错、空 catch、静默 fallback 或返回伪成功。服务端校验身份、权限和输入；日志脱敏。新依赖、全局配置、数据库迁移、公共契约变更需做影响分析和审批。

## 6. Vue 3 组件化专项规范

默认基线为 Vue 3 + TypeScript；项目版本和现有约定优先。

### 6.1 组件职责分层

| 类型 | 主要职责 | 不应承担 |
|---|---|---|
| Page/View | 页面级编排、路由参数、数据组合 | 大量领域规则、所有子区域实现 |
| Feature/Business Component | 明确业务概念、局部交互和状态 | 跨模块编排、重复 API 客户端 |
| Shared UI Component | 通用展示/交互、稳定变体 | 业务 API、具体路由、业务权限决策 |
| Composable (useXxx) | 可复用响应式逻辑、状态转换、副作用生命周期 | 模板渲染、无界全局状态 |
| API/Service | 请求、DTO 映射、错误映射、取消 | 页面布局和 UI 渲染 |
| Store (Pinia) | 必要的跨页面共享状态 | 所有临时状态、重复保存同一事实 |
| Types | Props、DTO、领域类型、事件契约 | any 或不一致的重复定义 |

### 6.2 必须遵循的组件化原则
- 页面负责组合，子组件负责明确职责；复杂 SFC 按业务区域和变化原因拆分。
- Props 输入、Emits 输出、Slots 扩展；子组件不得直接修改 Props 或依赖父组件内部实现。
- 公共组件 API 最小且稳定，避免大量布尔 Props、页面特判和万能组件。
- 两处以上相同结构/行为是复用候选；确认业务语义和变化原因一致后抽取。
- 表格、筛选、分页、表单、弹窗、空态、错误态先查项目组件库。
- 共享组件 API 变化必须检索调用点并做兼容/回归测试。

### 6.3 Vue 3 + TypeScript 编码规则
- 按项目约定优先 script setup、Composition API 和显式类型。
- Props/Emits 明确声明；不直接修改 Props。
- 可复用逻辑进入命名清晰的 Composable；派生状态用 computed，watch 仅用于必要副作用。
- API 调用集中到 API client/service，不在各组件重复 URL、鉴权、错误解析。
- Pinia 仅用于明确跨页面共享状态；局部状态留在组件。
- v-for 使用稳定业务 key；复杂模板逻辑提取到 computed/函数。
- 处理加载、空、错误、禁用、无权限、重复提交、取消和请求竞态。
- 组件卸载清理监听器、订阅、定时器和请求；避免内存泄漏。
- 样式复用设计 Token，避免全局污染、无理由深度穿透和重复硬编码。
- 测试 Props/Emits/Slots、交互、错误状态、Composable 和关键用户流程。

## 7. 后端与 FastAPI 专项规范
- Router 负责 HTTP 协议、依赖注入、请求/响应模型和状态码；复杂业务逻辑放应用服务/领域服务。
- Pydantic 模型定义输入输出边界；数据库模型不直接作为公共 API 响应契约。
- Repository/DAO 负责持久化；业务规则不散落在 ORM 查询和路由函数。
- 服务端强制认证授权和输入校验；明确分页、排序、错误码、幂等和并发语义。
- 数据模型变化提供迁移脚本、兼容窗口和回滚/修复方案。
- 外部服务调用封装客户端，配置 timeout、重试上限、错误分类和可观测性。
- 日志脱敏；异步任务定义状态、幂等键、重试和失败恢复。

## 8. 测试与质量门禁
单元测试验证领域规则、纯函数、Composable、Service；组件测试验证 Props/Emits、交互和状态；API/契约测试验证 Schema、错误语义、权限和兼容性；集成测试验证 DB、缓存、消息队列和外部依赖；E2E 覆盖关键用户流程；静态检查包括 lint、类型、复杂度、安全与依赖；构建验证生产资源。新增逻辑应有测试；缺陷修复优先先建立失败用例。共享组件/API/服务变更检查所有调用方。只执行项目实际存在的命令并记录命令、工作目录、退出码、日志路径和版本。未运行写 NOT_RUN，环境阻塞写 BLOCKED，证据不足写 UNKNOWN。

## 9. 开发完成审查清单
- [ ] 需求、设计、实现和测试可追溯。
- [ ] 已搜索相似实现并记录复用决策。
- [ ] 组件/模块/服务职责清楚，依赖方向合理。
- [ ] 无不必要重复代码、万能抽象或过度拆分。
- [ ] 类型、错误、权限、副作用和状态处理完整。
- [ ] 共享组件/API 变更已检查调用点。
- [ ] 新增/修改逻辑有适用测试。
- [ ] 接口、设计、实现地图和使用文档已同步。
- [ ] 最终 Diff 不越权、不覆盖用户修改。
- [ ] 验证状态有真实证据，未执行项明确标记。

## 10. 交付要求
说明需求/设计依据、复用清单、模块/组件职责、变更文件、测试与构建命令及结果、文档同步、未执行项、剩余风险和回滚方式。代码修改完成不等于验证通过；静态检查不等于浏览器验收；模型自述不等于证据。

# AIMES 本地治理 CLI 技术设计与实现规范 V1.0

-   **文档编号**：AIMES-TECH-CLI-001
-   **版本**：V1.0
-   **状态**：技术设计基线（待选定试点项目验证）
-   **关联规范**：AIMES-SPEC-001《AI 多工具协同开发与工程知识治理规范
    V1.0》
-   **目标**：将项目规则、文档检查、追溯校验、任务交接和临时文件审计转化为可重复运行的本地工具。

> 本文描述待建设的
> CLI。命令、目录和数据结构是设计约定；在实现、测试并在目标项目验证之前，不应宣称功能已可用。

------------------------------------------------------------------------

## 1. 设计目标

### 1.1 必须具备的能力

1.  识别项目根目录并读取 AIMES 配置。
2.  检查文档元数据、链接和必需文件。
3.  校验追溯注册表的 ID 唯一性、关系完整性、路径存在性与状态证据。
4.  生成项目现状报告和任务上下文包。
5.  创建任务、交接记录和验证记录的模板。
6.  审计临时文件、输出清理候选，并支持安全预览。
7.  运行项目配置的验证命令白名单。
8.  输出人类可读报告和机器可读 JSON。
9.  提供明确退出码，便于 CI 集成。

### 1.2 首版不做

-   不自动重构业务代码。
-   不自动批准需求、架构决策或设计变更。
-   不在没有证据时自动把状态改成 `VERIFIED`。
-   不执行模型自由生成的任意 shell 命令。
-   不自动删除正式文档、测试、迁移、部署、运行数据或用途不明文件。
-   不依赖云端服务；首版以本地仓库为核心。
-   不假设特定 AI 工具的私有接口稳定可用。

### 1.3 设计原则

-   **只读优先**：先做审计与报告，再逐步增加写操作。
-   **显式配置**：验证命令、清理目录、必需文档由项目配置。
-   **可复现**：相同代码和配置应得到可解释的检查结果。
-   **可审计**：报告包含时间、commit、扫描范围、规则版本和失败项。
-   **安全默认值**：不确定即报告，不猜测、不删除。
-   **渐进接入**：旧项目可以先接入一部分文档与追溯，不要求一次迁移完成。

## 2. 技术选型建议

首版采用与项目技术栈相适配的实现语言，不为工具本身引入过重依赖。

  ---------------------------------------------------------------------------------------
  场景                    推荐实现                原因
  ----------------------- ----------------------- ---------------------------------------
  多技术栈通用 CLI        Python 3.11+            YAML、Markdown、Git、文件审计生态成熟

  纯 Node/TS 项目         TypeScript + Node.js    与项目工具链一致，便于复用 TS/JS AST
                          22+                     

  试点快速验证            Python 脚本 +           先验证治理模型，再决定是否封装安装包
                          `pyproject.toml`        

  CI                      项目现有 CI             避免早期额外建设平台
  ---------------------------------------------------------------------------------------

**推荐首个原型使用 Python**，但若选定项目已有成熟的 Node/TypeScript
工具体系，也可采用 TypeScript。两种实现应遵守相同的命令语义和 JSON
报告结构。不要在第一阶段同时实现两套 CLI。

建议 Python 依赖按需引入，例如 YAML 解析、Markdown
链接检查；能用标准库完成的功能不引入额外依赖。具体依赖版本应在实现时锁定并通过安全检查。

## 3. 配置与目录

### 3.1 配置文件

建议在项目根目录放置 `.aimes/config.yaml`：

``` yaml
schema_version: 1

project:
  id: DSH
  name: DSH Web AI Provider Plugin
  language: zh-CN

paths:
  docs: docs
  traceability: traceability
  tasks: project-control/tasks
  handoffs: project-control/handoffs
  temp_registry: .aimes/temp-registry.yaml
  reports: .aimes/reports

checks:
  required_docs:
    - README.md
    - AGENTS.md
    - docs/01-business/business-overview.md
    - docs/02-requirements/module-catalog.md
    - docs/03-architecture/overall-architecture.md
    - docs/10-project-state/current-state.md
  require_doc_frontmatter: false
  verify_code_paths: true
  verify_symbols: false
  require_test_mapping_for_critical_features: true

verification:
  commands:
    - id: lint
      command: ["pnpm", "lint"]
      enabled: false
    - id: test
      command: ["pnpm", "test"]
      enabled: false
    - id: build
      command: ["pnpm", "build"]
      enabled: true
  timeout_seconds: 900

cleanup:
  allowed_roots:
    - .aimes/tmp
    - .aimes/artifacts
  dry_run_by_default: true
  require_registry: true
  never_delete:
    - docs
    - tests
    - migrations
    - deploy
    - .github
```

配置示例中的项目名称、路径和命令仅用于演示。初始化时必须根据真实仓库生成或由用户确认；不得把示例命令当成项目已经支持的命令。

### 3.2 建议目录

``` text
project/
├── .aimes/
│   ├── config.yaml
│   ├── temp-registry.yaml
│   ├── reports/
│   ├── contexts/
│   └── tmp/
├── scripts/
│   └── aimes/                 # 若项目采用脚本入口
├── docs/
├── project-control/
│   ├── tasks/
│   └── handoffs/
└── traceability/
    ├── modules.yaml
    ├── features.yaml
    ├── requirement-links.yaml
    ├── code-links.yaml
    └── test-links.yaml
```

项目可以使用已有目录；CLI 应允许配置覆盖默认路径，不得强制迁移已有文档。

### 3.3 配置校验

CLI 启动时应校验：

-   `schema_version` 是否受支持；
-   路径是否为相对项目根目录的路径（需要访问项目外部时应显式配置并警告）；
-   命令是否为参数数组，不使用 shell 拼接执行；
-   清理根目录是否处于项目根目录内；
-   `never_delete` 保护规则是否覆盖正式资产目录；
-   是否存在未知配置项，并以警告或严格模式错误呈现。

## 4. 命令行接口

### 4.1 命令总览

  命令                     主要用途                     默认是否修改文件
  ------------------------ ---------------------------- ------------------
  `aimes init`             初始化配置与最小目录         是，先预览
  `aimes project report`   汇总项目状态                 否
  `aimes docs check`       检查文档结构与链接           否
  `aimes trace check`      检查追溯注册表               否
  `aimes task create`      创建任务模板                 是，新建文件
  `aimes context build`    生成任务上下文包             是，生成文件
  `aimes task handoff`     生成交接草稿                 是，新建文件
  `aimes task resume`      生成任务恢复摘要             可选生成文件
  `aimes verify`           运行已配置的检查命令         运行进程
  `aimes cleanup audit`    生成清理候选报告             否
  `aimes cleanup safe`     清理满足白名单条件的临时项   是，受控删除
  `aimes report`           汇总治理结果                 否/生成报告

### 4.2 通用选项

建议所有适用命令支持：

-   `--root PATH`：项目根目录；默认从当前目录向上探测。
-   `--config PATH`：指定配置文件。
-   `--format text|json`：报告格式。
-   `--output PATH`：将报告写入指定路径。
-   `--strict`：将指定级别的警告提升为失败。
-   `--quiet`：仅输出错误与最终状态。
-   `--version`：输出 CLI 与 schema 版本。

任何写入/删除命令都应支持 `--dry-run` 或等价预览选项。清理命令默认
dry-run。

### 4.3 示例

``` bash
aimes project report
aimes docs check --format json --output .aimes/reports/docs-check.json
aimes trace check --strict
aimes context build TASK-DSH-012
aimes task handoff TASK-DSH-012
aimes cleanup audit
aimes cleanup safe --dry-run
aimes verify --profile ci
```

这些是目标命令示例，必须在 CLI 实际实现后才能执行。

## 5. 内部模块设计

建议分为以下模块，避免命令入口直接混合文件扫描、业务规则和输出逻辑。

``` text
aimes/
├── cli.py                  # 参数解析与命令分发
├── config.py               # 配置读取、默认值与校验
├── project.py              # 项目根目录与 Git 信息
├── models.py               # 内部数据模型、问题、报告
├── docs/
│   ├── scanner.py
│   ├── frontmatter.py
│   └── links.py
├── trace/
│   ├── loader.py
│   ├── validator.py
│   └── code_refs.py
├── tasks/
│   ├── create.py
│   ├── context.py
│   └── handoff.py
├── verify/
│   ├── runner.py
│   └── evidence.py
├── cleanup/
│   ├── scanner.py
│   ├── policy.py
│   └── executor.py
├── reports/
│   ├── text.py
│   └── json.py
└── tests/
```

### 5.1 模块职责

-   `cli`：只处理参数、调用服务和设置退出码。
-   `config`：读取配置、校验路径和命令白名单。
-   `project`：定位仓库、获取 commit、分支和工作区状态。
-   `docs`：扫描文档元数据、必需章节、内部链接。
-   `trace`：加载注册表、校验实体、关系和代码引用。
-   `tasks`：创建任务、生成上下文包和交接草稿。
-   `verify`：执行白名单命令并保存退出码、耗时、输出位置。
-   `cleanup`：候选扫描、策略判定、预览和受控执行。
-   `reports`：统一输出 text/JSON，避免每个模块各自定义格式。

## 6. 数据模型

### 6.1 检查问题 Finding

``` json
{
  "rule_id": "TRACE-REF-001",
  "severity": "error",
  "message": "feature 引用了不存在的 requirement ID",
  "path": "traceability/features.yaml",
  "line": 12,
  "entity_id": "FEAT-DSH-001",
  "related_ids": ["REQ-DSH-999"],
  "suggestion": "核实 ID，或在需求注册表中补充有效实体"
}
```

字段说明：

-   `rule_id`：稳定规则编号。
-   `severity`：`error`、`warning` 或 `info`。
-   `message`：面向人的问题描述。
-   `path`、`line`：尽可能定位到来源。
-   `entity_id`、`related_ids`：相关治理实体。
-   `suggestion`：建议动作，不自动替代人工决策。

### 6.2 检查报告

``` json
{
  "schema_version": 1,
  "tool": "aimes",
  "tool_version": "0.1.0",
  "check_id": "trace-check",
  "generated_at": "2026-01-01T00:00:00Z",
  "project_root": ".",
  "git": {
    "branch": "feature/example",
    "commit": "abcdef0",
    "worktree_dirty": true
  },
  "summary": {
    "errors": 0,
    "warnings": 2,
    "infos": 4,
    "result": "warning"
  },
  "findings": []
}
```

时间、分支、commit
和统计值应由程序真实采集；示例值不得被复制为真实结果。报告不得包含密钥、Cookie、访问令牌或敏感环境变量。

### 6.3 验证证据

每次运行验证命令应记录：

``` yaml
verification_runs:
  - run_id: VERIFY-2026-001
    task_id: TASK-DSH-012
    command_id: build
    started_at: "2026-01-01T00:00:00Z"
    finished_at: "2026-01-01T00:03:00Z"
    exit_code: 0
    result: passed
    commit: abcdef0
    log_path: .aimes/reports/VERIFY-2026-001-build.log
```

日志路径和结果由执行器真实生成。应设置日志大小限制，并对疑似凭据进行脱敏。无法确认脱敏安全时，不应把完整环境变量或命令环境写入日志。

## 7. 文档检查器设计

### 7.1 检查项

-   配置列出的必需文档是否存在；
-   正式文档是否包含要求的 ID、标题、版本、状态等元数据；
-   状态值是否符合规范；
-   内部相对链接是否可解析；
-   文档中声明的关联 ID 是否存在（可复用追溯模块）；
-   自动生成文档是否标记生成来源；
-   重复权威文档候选（首版仅提示，不自动合并）。

### 7.2 检查策略

-   默认将缺失必需文档、非法状态和断链列为 error。
-   可选元数据缺失列为 warning，项目开启严格模式后再提升等级。
-   不应要求所有 Markdown 都具有相同的元数据；可按目录或 glob 配置规则。
-   外部 URL
    默认不做在线可用性判断，以保持离线、可复现；需要时单独配置网络链接检查。
-   Markdown 解析失败时应给出文件路径与行号，不应静默跳过。

## 8. 追溯校验器设计

### 8.1 输入

首版支持 YAML 注册表。可根据项目规模逐步加入 JSON
或数据库，但不能在同一项目内无规则地维护多个互相冲突的事实源。

### 8.2 校验规则

  规则 ID            严重级别        检查内容
  ------------------ --------------- ------------------------------
  TRACE-ID-001       error           ID 缺失或重复
  TRACE-REF-001      error           关联 ID 不存在
  TRACE-PATH-001     error/warning   代码路径不存在
  TRACE-FEAT-001     warning/error   关键功能缺少需求关联
  TRACE-CODE-001     warning/error   关键功能缺少实现映射
  TRACE-TEST-001     warning/error   关键功能缺少测试映射
  TRACE-VER-001      error           VERIFIED 状态缺少有效证据
  TRACE-STALE-001    warning         映射指向已移动或疑似过期路径
  TRACE-ORPHAN-001   info            未被其他实体引用的注册项
  TRACE-DOC-001      warning         文档中出现未注册的追溯 ID

### 8.3 符号校验分级

-   **Level 1**：仅验证文件路径存在。
-   **Level 2**：对 Python/TypeScript/JavaScript 等语言解析符号名。
-   **Level 3**：结合 AST、模块依赖和测试发现做影响分析。

首版建议实现 Level 1，避免把简单字符串搜索误认为可靠的符号解析。Level
2/3
应使用对应语言解析器，并保留动态导入、反射和运行时注册导致的盲区说明。

## 9. 项目报告与上下文包

### 9.1 项目状态报告

建议包含：

-   项目 ID、Git 分支、commit、工作区是否干净；
-   模块数量及状态分布；
-   需求和关键功能状态分布；
-   追溯检查错误/警告数量；
-   最近验证结果和未通过的门禁；
-   当前任务、阻塞项和已知问题；
-   文档健康度和临时文件审计摘要；
-   扫描范围、未扫描范围和报告生成时间。

如果某项数据没有登记，应输出"未知/未采集"，不能通过模型推断补齐。

### 9.2 上下文包生成

`aimes context build TASK-ID` 的建议流程：

1.  读取任务文件并验证任务 ID。
2.  提取关联需求、模块、功能、设计、ADR 和测试 ID。
3.  从追溯注册表获取相关代码路径和测试路径。
4.  加入项目规则、当前状态、已知问题和最近交接。
5.  检查所有路径存在性与文件大小限制。
6.  生成 Markdown
    索引，默认不复制整个源代码；必要时只摘录明确限定的相关片段。
7.  输出缺失资料和过期引用警告。
8.  将生成文件写入 `.aimes/contexts/`，并标注生成时间和基线 commit。

上下文包是导航材料，不是事实源。执行任务前，AI
仍需在工作区核实实际代码和 Git 状态。

## 10. 任务与交接生成

### 10.1 任务创建

任务创建应要求至少提供标题、目标、验收标准和优先级。可允许暂缺关联
ID，但需标注待补全，不能默认为已完成追溯。

任务文件命名建议：`project-control/tasks/TASK-<项目>-NNN.md`。

任务 ID 生成必须防止冲突：读取现有任务与注册表，确认 ID
未使用后再创建；若并发环境可能发生竞争，应使用文件锁或要求单写入者。

### 10.2 交接生成

CLI 可以根据 Git
状态、任务记录、验证报告和追溯结果填充交接草稿，但下列内容必须来自真实数据或明确标为待确认：

-   当前 commit 和工作区状态；
-   实际变更文件；
-   实际运行的命令和退出码；
-   验证证据位置；
-   未解决问题。

CLI 不应把模型生成的"已完成"描述直接写入权威状态而不校验。

## 11. 验证命令执行器

### 11.1 安全要求

-   命令必须在项目配置白名单中。
-   以参数数组执行，避免 shell 字符串拼接。
-   不允许通过 CLI 参数临时注入任意命令。
-   设置超时、输出大小上限和明确工作目录。
-   记录退出码、开始/结束时间、commit 和日志路径。
-   不默认记录全部环境变量。
-   执行部署、数据库迁移、发布、数据删除等高风险操作时，应由项目独立审批流程管理，不放入普通
    `verify` 默认配置。

### 11.2 结果语义

-   `passed`：进程退出码成功，且该检查本身没有报告失败。
-   `failed`：命令运行并明确失败。
-   `blocked`：依赖、权限或环境原因无法运行。
-   `not_run`：未执行。
-   `partial`：仅部分检查完成。

`passed` 仅代表该命令的检查范围通过，不能推导整个项目无缺陷。

## 12. 临时文件清理器

### 12.1 审计阶段

清理审计至少收集：

-   路径、文件类型、大小、修改时间；
-   是否位于允许清理根目录；
-   是否在临时登记表中；
-   是否被追溯注册表或已知配置引用；
-   是否存在 Git 未跟踪或未提交修改；
-   是否属于保护目录/文件类型；
-   是否可再生成（仅当有明确规则时）；
-   建议等级与理由。

首版不必实现复杂的全语言引用分析。应明确报告扫描范围，并把不确定项交给人工。

### 12.2 安全删除判定

只有同时满足以下条件才可自动删除：

1.  文件在登记表中；
2.  位于配置的允许清理根目录内；
3.  未命中保护规则；
4.  未发现有效引用；
5.  已超过配置的保留期；
6.  被规则明确标记为可再生成或可丢弃；
7.  `--dry-run` 预览结果已确认，或项目明确允许满足条件的 A
    级项自动清理。

任何条件不满足时，只能列入人工复核。符号链接、路径穿越、目录外目标和异常路径一律拒绝处理。

### 12.3 防误删机制

-   解析真实路径后再次确认其仍在允许根目录下。
-   不跟随指向目录外的符号链接。
-   不递归删除未登记的整个目录。
-   执行前再次检查 Git 状态和文件属性。
-   清理报告先写入独立位置，保留删除清单。
-   支持 `--dry-run`、`--limit N` 和明确的确认选项。
-   清理失败时停止当前批次或按明确策略继续，并记录每个项目的结果。

------------------------------------------------------------------------

## 13. 退出码与 CI 集成

建议退出码：

  退出码   含义
  -------- ----------------------------------
  `0`      检查通过，没有达到失败阈值的问题
  `1`      检查发现 error 或验证命令失败
  `2`      配置、参数或注册表格式错误
  `3`      环境/依赖阻塞，无法完成检查
  `4`      安全策略拒绝执行写入或清理操作
  `5`      内部异常，需查看诊断信息

CI 推荐顺序：

1.  配置校验；
2.  文档检查；
3.  追溯检查；
4.  项目原有 lint/typecheck/test/build；
5.  汇总报告；
6.  仅上传报告，不在普通 CI 中清理工作区。

初期可以将部分追溯缺口设为
warning；当注册表稳定后，再对关键功能的缺失关系启用严格门禁。不得为了让
CI 通过而删除检查规则或把 error 静默降级。

------------------------------------------------------------------------

## 14. 测试设计

CLI 自身必须有测试，至少覆盖以下场景：

### 14.1 配置测试

-   配置文件缺失、语法错误、schema 版本不支持；
-   相对路径越界和非法清理根目录；
-   验证命令不在白名单；
-   未知配置项在普通/严格模式下的行为。

### 14.2 文档检查测试

-   必需文档缺失；
-   合法/非法状态值；
-   内部链接有效与失效；
-   元数据缺失；
-   Unicode 中文路径和空格路径。

### 14.3 追溯测试

-   重复 ID；
-   悬空引用；
-   代码路径缺失；
-   关键功能缺少测试映射；
-   VERIFIED 缺少证据；
-   空注册表、部分注册表和未知字段。

### 14.4 验证执行器测试

-   成功命令、失败命令、超时命令；
-   大量 stdout/stderr；
-   命令不存在；
-   不允许执行的命令被拒绝；
-   日志脱敏与输出截断。

### 14.5 清理器安全测试

-   已登记且过期的临时文件；
-   未登记文件；
-   正式文档和测试文件；
-   未提交修改；
-   指向目录外的符号链接；
-   `../` 路径穿越；
-   同名文件和空目录；
-   dry-run 不产生删除；
-   删除失败后报告准确。

### 14.6 端到端验收

建立一个临时测试仓库，植入重复
ID、断链、失效路径、缺少测试映射和过期临时文件，确认 CLI
能发现问题；再验证它不会删除正式文档或未提交用户文件。

------------------------------------------------------------------------

## 15. 实施阶段与交付件

### CLI-0：骨架与配置

-   CLI 入口、配置模型、项目根目录发现、统一报告和退出码。
-   交付：可运行的 `--help`、配置校验和最小测试。

### CLI-1：文档与追溯只读检查

-   Markdown 必需文件/链接检查。
-   YAML 注册表解析、ID 和引用检查、路径存在性检查。
-   交付：`docs check`、`trace check`、JSON 报告和测试。

### CLI-2：项目报告与任务上下文

-   Git 信息、模块/功能状态汇总。
-   任务创建、上下文包、交接草稿。
-   交付：可恢复任务所需的基本工具链。

### CLI-3：验证执行器

-   白名单命令、超时、日志、结果证据。
-   交付：`verify` 与可审计验证记录。

### CLI-4：清理审计

-   临时登记表、候选分类、保护规则和 dry-run。
-   交付：`cleanup audit` 与清理安全测试。

### CLI-5：受控清理与 CI

-   仅对满足安全条件的 A 级项执行清理。
-   CI 集成、门禁配置和完整验收。
-   交付：试点项目的稳定治理流程。

------------------------------------------------------------------------

## 16. CLI 首版完成定义

只有同时满足以下条件，才能称首版 CLI 试点完成：

-   [ ] 在选定项目的干净环境中可安装/运行。
-   [ ] 配置校验有完整测试。
-   [ ] 文档检查可发现缺失文件和断链。
-   [ ] 追溯检查可发现重复 ID、悬空引用和无效路径。
-   [ ] JSON 报告结构有版本号且字段稳定。
-   [ ] 退出码在 CI 中行为明确。
-   [ ] 验证执行器只执行白名单命令。
-   [ ] 清理器通过未登记文件、正式资产、未提交修改和路径穿越测试。
-   [ ] 报告包含真实 Git 基线和真实验证结果。
-   [ ] 在真实试点仓库完成至少一次跨工具交接验证。
-   [ ] 所有未实现能力均明确列出，没有以设计文档冒充已实现功能。

------------------------------------------------------------------------

## 17. 推荐实施顺序

1.  选定一个试点仓库，优先选择具有实际多工具协作需求、但改动风险可控的项目。
2.  先做资产盘点和文档基线，不先大规模重排目录。
3.  手工建立少量关键模块、需求、功能、代码和测试的追溯关系。
4.  实现 `docs check` 与 `trace check`，以只读方式验证治理模型。
5.  根据试点反馈修订规范与注册表，再增加任务上下文和交接生成。
6.  最后实现验证执行器、清理审计、受控清理和 CI。
7.  试点稳定后，再扩展到其他项目与 ZCode、Trae Code、VS Code 等工具。
8.  数据模型和命令接口稳定后，才考虑可视化治理工作台。

**关键决策：先把"项目事实如何表达与验证"做正确，再把"如何自动化执行"做高效。**

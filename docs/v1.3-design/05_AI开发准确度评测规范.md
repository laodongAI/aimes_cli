# AIMES AI 开发准确度评测规范（提案）

- **文档编号**：AIMES-EVAL-1301
- **状态**：DRAFT / 待评审

## 1. 目标

评估提示词、Skills、上下文策略和模型/工具组合是否实际提升了 AI 工程任务表现。评测不以模型自评、输出长度、文档数量或单次成功作为充分证据。

## 2. 评测层级

1. **单元级**：检查 Skill 输入/输出契约、Schema、路径引用、状态和元数据。
2. **案例级**：对固定需求/项目任务检查需求识别、复用决策和输出质量。
3. **工程级**：在隔离仓库/分支运行测试、构建、静态检查和独立验收。
4. **工具接入级**：验证规则实际加载、上下文恢复、权限边界、用户修改保护和真实命令证据。
5. **回归级**：修改 Skill、提示词、模型或适配器后重跑基准集，检查是否退化。

## 3. 核心评测集分类

### 需求认知
- 描述完整、边界明确的常规需求；
- 缺少关键验收标准的需求；
- 存在多个合理解释的歧义需求；
- 与项目权威文档冲突的需求；
- 隐含权限、安全、兼容、幂等或并发约束；
- 用户中途变更需求并要求评估影响的案例。

### 项目知识复用
- 项目中存在可直接复用的公共组件；
- 存在相似但不适用的旧方案；
- 旧方案已过时或被 ADR 替代；
- 需要适配而不能原样复制的场景；
- 历史缺陷包含可复用根因与回归测试；
- 搜索未命中时必须正确报告未知，不能编造路径/符号；
- 新场景违反旧方案前置条件，需要拒绝复用。

### 工程治理
- 工作区存在未提交用户修改；
- 测试未运行或环境阻塞；
- 工具规则文件无法读取；
- 追溯引用故意设置为无效；
- Skill 输出缺少必需字段；
- 跨工具交接信息与当前仓库事实不一致。

## 4. 评测案例格式

```yaml
schema_version: 1
case_id: EVAL-REQ-001
suite: requirement-cognition-baseline

initial_state:
  repository_fixture: "fixture path or commit"
  git_state: "clean or specified diff"
input:
  task: "user request"
  allowed_context: []
expected:
  required_findings: []
  forbidden_claims: []
  expected_questions: []
  expected_reuse_decision: null
  acceptance_checks: []
scoring:
  hard_gates: []
  diagnostic_dimensions: []
references:
  source_docs: []
  hidden_tests: []
```

评测案例应记录可复现初始状态、允许的上下文、参考答案/判定标准、隐藏验收检查和版本。若实现存在多种正确方案，应定义允许的行为集合，不以单一代码文本匹配评判正确性。

## 5. 指标定义

| 指标 | 建议计算方式 | 注意事项 |
|---|---|---|
| 关键需求召回率 | 正确识别的标注关键需求/全部标注关键需求 | 需人工标注基准；不能用模型自评代替 |
| 关键歧义识别率 | 正确识别的阻断级歧义/全部标注阻断级歧义 | 需记录漏报和误报 |
| 误推断率 | 被当成事实的无依据主张/全部被判定的事实主张 | 同时报告样本量与严重程度 |
| 验收可判定率 | 可由独立人员/脚本判定的关键验收项/全部关键验收项 | “清晰、友好、完善”等需操作化 |
| 相关资产召回率 | 找到的标注相关资产/全部标注相关资产 | 不能将检索数量当召回率 |
| 复用决策正确率 | 正确的 REUSE/ADAPT/TRANSFER/DO_NOT_REUSE 判断/全部已标注案例 | 需包含“看似相似但不适用”反例 |
| 重复实现率 | 在存在合适可复用资产时仍新增重复实现的案例/适用案例 | 明确什么算重复实现 |
| 迁移验证通过率 | 迁移方案通过独立验收的案例/实际执行迁移案例 | 同时报未执行和环境阻塞 |
| 同类缺陷复发率 | 同一根因再次出现的案例数/相关后续变更或运行数 | 需根因分类稳定 |
| 证据完整率 | 有效证据支持的 VERIFIED 项/全部 VERIFIED 项 | 虚构或不可定位证据按无效处理 |
| 用户修改保护率 | 未覆盖受保护修改的案例/含用户修改案例 | 破坏性测试必须隔离 |

## 6. 硬门禁与诊断评分

硬门禁不能通过其他维度的高分抵消。示例硬门禁：

- 未经确认的阻断级歧义不得被当作已批准需求；
- 不得编造代码路径、工具执行、测试结果或审批；
- 不得覆盖受保护的用户改动；
- 高风险操作必须遵循审批要求；
- `VERIFIED` 必须有真实、可定位的验证证据；
- 复用方案不得忽略已知的不适用条件和安全约束。

诊断分可用于比较版本，但必须报告维度、样本量、失败案例、模型/工具版本和上下文配置。禁止只发布综合分数而隐藏硬门禁失败。

## 7. 对照实验设计

比较 Skill/提示词改动前后时：

- 固定评测案例和仓库初始状态；
- 记录模型、模型版本、工具版本、运行模式、系统提示词/Skill 版本和上下文来源；
- 尽量控制其他变量；
- 对随机性明显的模型任务进行多次运行或抽样；
- 使用独立测试/盲审降低“同一模型生成又自评”的偏差；
- 保存原始结果和失败样本，不能只保留成功截图；
- 对评测集的泄漏和过拟合进行管理，保留未公开/留出的验收案例。

## 8. 失败分类

建议统一分类：`REQ_MISUNDERSTOOD`、`CONTEXT_MISSING`、`CONTEXT_STALE`、`REUSE_MISAPPLIED`、`DUPLICATE_IMPLEMENTATION`、`ARCHITECTURE_DRIFT`、`IMPLEMENTATION_DEFECT`、`TEST_GAP`、`EVIDENCE_INVALID`、`TOOL_RULE_NOT_LOADED`、`USER_CHANGE_OVERWRITTEN`、`SKILL_CONTRACT_VIOLATION`、`ENVIRONMENT_BLOCKED`、`OTHER`。

失败分类是分析标签，不替代 AIMES 全局状态。每次根因复盘至少记录：可复现证据、直接原因、系统性原因、影响、修复、是否需修改需求/Skill/提示词/门禁/知识资产，以及对应回归案例。

## 9. 发布准则

Skill/提示词版本发布前至少满足：

- 契约校验通过；
- 所有硬门禁案例通过；
- 核心指标没有超过预设容忍值的退化；
- 新增失败有明确解释和风险接受记录；
- 工具适配声明有对应版本/运行模式证据；
- 评测报告可复核。

具体阈值不在本提案中拍脑袋固定，应先收集基线数据，再由项目/治理责任人批准。V1.3 初期应先建立可复现测量，随后再设阈值。

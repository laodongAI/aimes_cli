# AIMES V1.3 总体设计与修订提案

- **文档编号**：AIMES-DESIGN-1301
- **状态**：DRAFT / 待评审
- **修订基线**：AIMES-SPEC-001 V1.2
- **定位**：设计提案，不替代当前正式治理规范

## 1. 设计目标

V1.2 已定义单一事实源、事实优先级、统一状态词表、跨工具适配、上下文与交接、风险分级、规则加载证据和交付报告。本次不推翻这些基础，而是把两项不足够具体的能力变成可执行的工程契约：

- **需求认知工程（RCE）**：从用户意图到经确认的需求基线。
- **项目知识复用工程（PKR）**：从项目资产发现到正确复用、适配、验证和沉淀。

并补齐使它们可持续运行的三个支撑面：

- **Skill 生命周期治理**：可注册、可版本化、可验证、可回归。
- **AI 开发准确度评测**：基于固定案例和真实证据评估效果。
- **CLI 可执行治理**：把可确定性检查转成机器检查，不将主观判断伪装为自动门禁。

## 2. V1.2 与 V1.3 的关系

| V1.2 既有原则/能力 | V1.3 的增强方式 | 是否替换既有定义 |
|---|---|---|
| 单一事实源、事实优先级 | 给需求、知识资产和 Skill 明确来源、权威性与新鲜度元数据 | 否 |
| 需求/模块/功能/设计/代码/测试追溯 | 增加需求认知记录、复用决策和迁移验证关联 | 否，扩展实体关系 |
| 统一状态词表 | 将需求审批、知识成熟度、实现验证拆为不同字段；状态值仍复用规范词表 | 否 |
| 上下文包与交接 | 增加上下文充分性、缺失/冲突/过期检查 | 否 |
| P01-P10 提示词治理 | 引入 Skill 注册表与执行契约；提示词可作为 Skill 的一种执行载体 | 否，需登记映射而非另起炉灶 |
| 风险等级与交付报告 | 将需求歧义、复用风险和验证缺口纳入风险输入 | 否 |
| 规则加载证据与工具适配矩阵 | 增加 Skill 执行证据、版本、运行模式与评测证据 | 否 |
| CLI 规划 | 增量增加需求/知识/Skill/评测元数据检查 | 不假定 V0.1.0 已实现这些能力 |

## 3. 核心架构

```text
AIMES Core（V1.2 统一治理原则）
  ├─ 需求认知工程 RCE
  │    ├─ 意图/显性需求提取
  │    ├─ 场景、规则、约束与歧义建模
  │    ├─ 项目事实对照
  │    └─ 需求充分性门禁与基线
  ├─ 项目知识复用工程 PKR
  │    ├─ 代码/文档/决策/测试/缺陷检索
  │    ├─ 适用性比较与复用决策
  │    ├─ 迁移计划与验证
  │    └─ 候选知识沉淀和成熟度管理
  ├─ Skill 生命周期治理
  │    ├─ 注册、契约、版本、权限和依赖
  │    └─ 验收、运行证据和回归评测
  ├─ 验证与准确度评测
  │    ├─ 独立验收与工程门禁
  │    ├─ 固定评测集与指标
  │    └─ 失败分类、根因和反馈
  └─ 工具适配层 / CLI / CI
       ├─ 加载统一规则和项目上下文
       ├─ 执行可确定性检查
       └─ 输出机器可读证据
```

## 4. 设计原则

1. **需求先于实现**：影响正确性、兼容性、安全或验收的关键歧义未解决时，暂停受影响的写操作；可继续不受影响的只读调查。
2. **项目知识先于新造**：开发前必须检索已有实现、接口、公共组件、ADR、测试和历史问题；检索不到不能直接证明不存在。
3. **相似不等于适用**：复用前必须比较目标、前置条件、约束、依赖、已知限制和验证方式。
4. **候选不等于权威**：模型推断和新总结默认是候选；需求由授权责任人批准，工程知识按规定证据/评审升级。
5. **规则与执行分离**：提示词/Skill 引导执行，脚本/测试/CI 验证可确定性事项，人审批高风险决策。
6. **单一事实源**：不得为需求认知或知识复用另建平行状态词表、第二套需求库或重复追溯权威。
7. **证据优先**：`VERIFIED` 只用于有可定位、可复核的真实证据的特定对象/范围。
8. **渐进实施**：先做 Markdown/YAML/JSON 契约和只读校验，不先引入图数据库、复杂向量平台或自治代理。
9. **工具能力实测**：所有工具专属加载、检索、命令和记忆能力都要按产品版本/模式验证。
10. **指标不能被刷分**：缺失关系、未知值和未运行验证必须显式呈现，不通过填充虚假关联或降低分母提高指标。

## 5. 新增治理对象（建议）

| 对象 | 建议 ID | 用途 | 权威来源建议 |
|---|---|---|---|
| 需求认知记录 | `RCN-<PROJECT>-NNN` | 记录输入、事实/推断/未知、场景、问题与结论 | 需求工作流产物；批准后引用正式需求 |
| 复用决策 | `RUD-<PROJECT>-NNN` | 记录复用/适配/不复用/新设计的依据 | 任务/设计记录，必要时进入 ADR |
| 知识资产 | `KNW-<PROJECT>-NNN` | 管理候选/已验证的可复用知识 | 知识注册表，引用权威源 |
| Skill | `SKL-<DOMAIN>-NNN` | 管理工作流、契约和评测 | Skill 注册表为元数据权威 |
| 评测案例 | `EVAL-<SUITE>-NNN` | 固定输入、初始状态、期望和评分规则 | 版本控制的评测集 |
| 评测运行 | `EVRUN-<PROJECT>-NNN` | 记录模型/工具/Skill 版本和结果 | 评测报告/机器可读结果 |

ID 格式是建议，须在批准前对照 V1.2 的 ID 兼容原则和项目既有格式确定。不能仅凭编号格式推断实体关系。

## 6. 字段边界：不要混用状态

建议将以下字段分开：

- `approval_status`：需求/决策的审批状态，沿用 AIMES 规范化状态值。
- `implementation_status`：实现事实状态，沿用规范化状态值。
- `validation_status`：特定范围的验证状态，沿用规范化状态值。
- `maturity`：知识资产的生命周期分级，如 `candidate`、`reviewed`、`validated`、`deprecated`。这是知识成熟度，不是 AIMES 通用状态，必须单独定义，不能伪装成全局状态枚举。
- `applicability`：知识资产适用条件、约束、例外和失效条件。

## 7. 工作流总图

```text
用户需求
  → 需求认知记录（事实/推断/未知）
  → 项目知识检索和现状核验
  → 歧义/冲突/风险检查
  → 需求充分性审查与批准
  → 影响分析和复用决策
  → 设计/实现计划
  → 受控实施
  → 独立验证与门禁
  → 更新追溯和项目状态
  → 候选知识沉淀
  → 评测回归与治理改进
```

## 8. V1.3 提案的边界

- 本提案不要求每个项目部署向量数据库、图数据库或完整知识图谱。
- 本提案不要求每项需求都由多 Agent 投票，不以模型数量代替责任人审批。
- 本提案不允许 AI 自行批准需求、架构决策或把候选知识升为权威。
- 本提案不假定模型能完整读取整个仓库；检索和上下文充分性必须记录证据与未知项。
- 本提案不将静态代码相似度直接视为复用建议正确性的证据。

## 9. 待评审决策

1. 新增 ID 前缀是否批准，还是复用现有 `REQ/TASK/DES/ADR` 实体扩展字段。
2. 知识注册表采用单一 YAML/JSON 索引 + 引用文件，还是按知识类别拆分文件；必须指定唯一权威。
3. Skill 文件采用标准化目录和 front matter，还是由唯一注册表生成元数据；建议注册表为元数据唯一权威，Skill 文件只保留 ID 和正文。
4. 需求质量是否采用硬门禁 + 诊断评分；建议高风险必需项硬门禁，其他指标只作诊断，不做简单平均。
5. 首批试点选择哪个仓库和任务；必须先确认基线、工具版本和实际规则加载方式。

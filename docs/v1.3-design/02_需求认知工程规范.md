# AIMES 需求认知工程规范（提案）

- **文档编号**：AIMES-RCE-1301
- **状态**：DRAFT / 待评审
- **目标**：让 AI 将自然语言需求转化为可确认、可设计、可实施、可验收的需求模型。

## 1. 能力定义

需求认知不是复述用户原话，也不是自动补全所有可能细节。它是有证据约束的过程：识别用户目标和显性要求，结合项目事实发现隐含约束，标出推断和未知，澄清关键歧义，形成可验证的需求基线。

## 2. 信息分类

| 分类 | 含义 | 允许的用法 |
|---|---|---|
| `CONFIRMED_FACT` | 用户明确确认或权威项目资料可证实的事实 | 可作为需求依据；记录来源 |
| `INFERENCE` | 根据事实推导出的合理解释 | 必须标记推断依据、影响和置信度；不能冒充批准事实 |
| `UNKNOWN` | 当前没有足够信息判断 | 保留未知；评估是否阻塞 |
| `CONFLICT` | 用户要求、权威文档、代码或不同来源存在冲突 | 并列呈现证据，按 V1.2 事实优先级处理，不擅自裁决需求 |
| `ASSUMPTION_PROPOSED` | 为推进讨论提出的候选假设 | 需责任人确认后才能成为需求基线 |

事实优先级继续遵循 V1.2。当前代码证明“现在怎样”，但不能自动决定“业务应该怎样”。

## 3. 标准工作流

### RCE-1：提取显性需求

提取业务目标、用户/角色、触发条件、输入、输出、主要行为、约束、明确不做事项、交付物和验收要求。保留原始用户表达或可追溯引用，避免在摘要中丢失限定词。

### RCE-2：构建业务场景

至少考虑适用的以下维度：

- 主成功路径；
- 失败/异常路径；
- 边界值和空值；
- 权限与信任边界；
- 状态转换与重复操作；
- 并发、重试、超时、取消和恢复；
- 数据一致性、幂等性、兼容性；
- 可观察性、审计和错误反馈。

并非每项需求都需要所有维度。AI 应标记适用、不适用及理由，避免机械生成冗长清单。

### RCE-3：核对项目事实

检索当前项目中的相关需求、业务规则、模块、接口、数据模型、架构决策、测试、缺陷和实现。列出实际读取的路径、ID 或符号。搜索不到只能说明“当前检索未找到”，不能直接断言“项目不存在”。

### RCE-4：识别歧义和冲突

每个问题记录：

- 歧义/冲突内容；
- 当前证据及来源；
- 可选解释；
- 对实现、兼容、安全和验收的影响；
- 是否阻止受影响写操作；
- 推荐澄清问题；
- 可先行开展的安全只读工作。

问题优先级：P0 阻断正确性/安全/数据/公共契约；P1 显著影响验收或范围；P2 影响体验或优化；P3 非关键偏好。优先级是本规范局部字段，不替换 AIMES 的全局风险/状态定义。

### RCE-5：生成结构化需求认知记录

以上是示意 Schema。正式版本必须在批准后固定必填字段、枚举、兼容策略和验证器规则。`status` 应使用 AIMES 规范化状态值；示例中的 `review_result` 不得另造与全局状态冲突的含义。

### RCE-6：需求充分性审查

按“硬门禁 + 诊断指标”两层检查，不使用单一平均分决定是否批准。

**建议硬门禁（按风险适用）：**

- 业务目标和预期结果可理解；
- 关键行为和验收条件可判定；
- 关键数据、安全、权限、兼容性约束没有未解决冲突；
- 关键歧义已澄清，或有明确授权的书面假设；
- 对公共接口、数据迁移和高风险操作有相应审批。

**诊断项：**

- 场景覆盖充分性；
- 边界/异常覆盖；
- 需求原子性和可追溯性；
- 术语一致性；
- 与现有需求/功能重复或冲突的可能性；
- 测试可设计性。

审查结果应给出每项依据、缺口和下一步。不能只输出“需求完整度 95%”而不说明证据。

## 4. 澄清策略

1. 先检索项目权威资料，避免问用户已经回答过的问题。
2. 只问会显著影响正确性、范围、风险或验收的关键问题。
3. 将相关问题合并为少量、明确的选择题或开放问题；不为省略思考而让用户填写冗长表格。
4. 对低风险、可逆、不会改变核心业务语义的细节，可提出默认建议并标记为待确认；不得将建议静默升级为批准需求。
5. 如果用户要求先推进，允许开展不受歧义影响的只读分析、测试盘点和方案比较；不实施被歧义直接影响的写操作。
6. 用户回答后更新需求认知记录，保留决策来源和时间，并重评受影响的需求、设计、测试和风险。

## 5. 需求变更传播

任何已确认需求变更都应分析：

`BUS/BPR → REQ → MOD/FEAT → DES/API/DATA → CODE → TEST → DELIVERY/EVIDENCE`

只更新真实受影响的实体，不为提高追溯率虚构关系。不能自动判断的关系标记为待确认并建立任务。

## 6. 完成判据

需求认知 Skill 只有在以下条件满足时才可报告“分析完成”：

- 已读取并列出相关权威资料；
- 显性需求和业务目标已提取；
- 关键场景与适用约束已分析；
- 事实、推断、未知、冲突分开记录；
- 关键歧义已解决，或明确标记为阻塞/待审批；
- 验收条件可检查；
- 与现有需求和实现的潜在关系已登记；
- 输出文件/记录可在项目中定位。

“分析完成”不等于“需求已批准”，也不等于“功能已实现”。

## 7. 失败模式与防护

| 失败模式 | 防护 |
|---|---|
| 过度提问 | 先检索项目资料，只问关键歧义 |
| 过度推断 | 标记推断、证据和待确认事项 |
| 需求文档写得很全但不可验收 | 要求每个关键要求有可观察的验收条件 |
| 把代码现状当成业务需求 | 将现状证据和目标规范分开陈述 |
| 用户变更后只改一段文字 | 执行变更影响分析和追溯更新 |
| 通过评分掩盖关键缺项 | 高风险硬门禁不允许被平均分抵消 |

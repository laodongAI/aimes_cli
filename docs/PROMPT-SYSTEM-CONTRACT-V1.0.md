# AIMES 提示词系统统一契约 V1.0

- 状态：实施基线；跨工具行为仍须试点验证
- 目的：为 Core、Skill、项目上下文、工具适配和评测定义单一、可核验的协作协议。

## 1. 分层与权威

1. **AIMES Core**：唯一公共治理权威，定义事实优先级、状态、权限、证据、审批和保护用户修改的底线。
2. **Skill**：只定义特定专业任务的触发、输入、步骤、决策、输出和专属失败路径；不得重新定义 Core 状态或权限。
3. **项目上下文**：记录项目自己的业务事实、架构、技术栈、路径映射、测试命令和责任人；与 Core 冲突时遵循权威规则并提出冲突。
4. **工具适配器**：仅声明某工具/版本/运行模式能实际执行的能力及降级方式。不得从工具名称推断规则已加载。
5. **评测层**：独立验证契约、输出、硬门禁和工程结果；不得让被测模型单独给自己打最终通过分。

## 2. 统一状态

- `PASS`：检查已执行，且满足事先定义的判据。
- `FAIL`：检查已执行，但不满足判据。
- `NOT_RUN`：尚未执行。
- `BLOCKED`：因权限、环境、依赖或外部条件无法执行。
- `UNKNOWN`：现有证据不足以判定。
- `PROPOSED`：候选建议，尚未获授权/批准。
- `APPROVED`：存在可定位的责任人批准证据；模型自述不构成证据。
- `VERIFIED`：仅在 AIMES 证据规则要求的真实、可定位验证证据存在时使用。

禁止状态升级：`NOT_RUN`、`BLOCKED`、`UNKNOWN` 不能推断为 `PASS`；`PROPOSED` 不能推断为 `APPROVED`；静态检查不能自动推断运行时行为。

## 3. 统一证据记录

关键结论建议使用如下字段（可按项目格式映射）：

```yaml
evidence_id: EVD-<stable-id>
claim: "被支持的具体主张"
status: PASS # PASS | FAIL | NOT_RUN | BLOCKED | UNKNOWN
source_type: file_inspection # file_inspection | runtime_observation | automated_check | user_confirmed | manual_prompt
source_path_or_uri: "实际来源；未知则显式标记"
locator: "行号、符号、测试名或报告定位"
observed_at: "时间或 UNKNOWN"
baseline: "commit/version/config or UNKNOWN"
limitations: []
```

`file_inspection` 只证明检查到的静态内容，不单独证明运行时规则加载、命令执行或功能正确。敏感值应脱敏，不把凭证写入日志或交接。

## 4. 统一决策模式

每个高影响结论都应回答：
1. 依据是什么？
2. 证据能证明什么、不能证明什么？
3. 有哪些替代解释/反例？
4. 如果判断错误，影响是什么？
5. 下一步是继续、询问、降级、阻断还是请求审批？

## 5. 输入与输出

- 必需输入须声明缺失处理；不得猜造 ID、路径、版本、审批和执行结果。
- 输出字段必须有定义；不适用写 `NOT_APPLICABLE` 并说明，无法判断写 `UNKNOWN`。
- 结构化记录必须由 Schema/CLI 校验；自然语言质量由独立案例评测与人工审查补充。
- 机器校验通过仅表示格式/规则检查通过，不等于内容事实真实或工程任务成功。

## 6. 工具执行与权限

- 先确认工具、版本、运行模式、当前项目根目录和可用能力。
- 先只读检索与计划，写操作遵循用户授权和项目门禁。
- 不可逆操作、生产动作、发布、数据迁移、权限变更及大范围删除必须按项目审批规则执行。
- 无法执行时明确降级到只读分析、人工验证或暂停，不伪造工具行为。

## 7. 上下文预算与 Token 效率

目标不是无条件压缩 Token，而是在硬门禁和工程质量不退化的前提下，减少无关上下文、重复读取、冗长交接和不必要的模型调用。

### 7.1 分层加载

- **L0 常驻护栏**：事实优先级、用户修改保护、授权/安全边界、状态与证据语义、验证要求、项目入口/恢复位置。
- **L1 任务材料**：按任务触发条件加载对应需求、设计、ADR、代码、测试、Skill 和运行手册。
- **L2 定向扩展**：只在证据不足、冲突、失败或影响范围扩大时增加读取范围，并说明扩展要解决的具体问题。

### 7.2 必须保留的硬门禁

不能为了节省 Token 而跳过工作区/用户修改检查、关键需求与批准核验、安全/权限/公共契约审查、必要测试与证据要求、合并前集成验证。预算不足时缩小非关键探索、分阶段处理或请求澄清，不得降低状态标准。

### 7.3 减少重复与交接成本

- 优先读索引、相关章节、代码符号和失败测试，不默认全量读取大型文件或整个仓库。
- 通过稳定路径、章节/符号定位、追溯 ID 和证据 ID 引用权威内容，不重复粘贴全文或完整日志。
- 交接摘要只保留目标、基线、关键事实/路径、保护清单、验证证据、未知、未执行项和下一步；详细分析留在任务报告中。
- 对每次跳过的专业 Skill，按编排协议记录适用性理由；不得因节省上下文而跳过硬门禁。

### 7.4 Token 数据与质量联合评估

- 真实模型/工具 usage 可用时，分别记录输入 Token、输出 Token、缓存 Token（若可用）和模型调用数。
- 没有真实 usage 时，标记 `UNKNOWN`；字符数、字节数或文件大小只能作为估算代理，不能称为实际 Token。
- 对比优化方案时，至少同时观察硬门禁失败、首次通过率、返工率、模型调用数和任务完成时间。
- 只有在硬门禁不退化、工程质量达到预设非劣标准时，Token 减少才算优化成功。

### 7.5 提示词能力非退化约束

- **不得把“减少提示词长度”当作独立优化目标。** 禁止为节省 Token 而大幅压缩或删除仍承担实际作用的业务约束、推理/执行步骤、领域方法、边界条件、反例、示例、异常分支、输出契约和验收标准。
- 只有在确认内容确实重复、其权威来源唯一且稳定、引用可定位，并且目标工具会在当前运行模式下实际读取该来源时，才可将重复正文替换为引用。仅写一个文件路径或链接，不等于模型已经加载其内容。
- 优先优化上下文路由、按需加载、重复内容注入、检索范围、交接格式和无效调用；不得通过省略任务必需的专业 Skill 或证据来达成预算目标。
- 提示词重构前后必须使用同一组代表性任务、同一验收标准和硬门禁进行对照。除 Token 外，还要检查需求覆盖、边界遵循、结果完整性、异常处理、测试质量、返工和完成时间。
- 若出现能力退化、遗漏增加、错误率上升或硬门禁失败，即使 Token 减少也判定优化失败；恢复必要提示内容或调整加载策略后重新评测。
- 对于尚未完成等效性评测的提示词精简，只能标记为 PROPOSED / NOT_RUN，不得宣称能力等价或优化成功。

## 8. 版本发布

每次提示词/Skill 改动记录版本、变更原因、契约差异、硬门禁变化、评测集版本、运行环境、结果和未验证限制。发布前执行结构校验、硬门禁案例和回归；真实工具适配声明必须有相应运行证据。初始版本的真实工具状态应保持 `UNKNOWN`，直至完成试点。

## 9. UI/UX 专业规则与触发契约

- 涉及页面设计、前端实现、布局/样式、组件、表单、导航、交互状态、响应式、无障碍或用户可见行为时，默认触发 `SKL-CORE-UI-001`（`skills/ui-quality-review/SKILL.md`）。
- Core 负责强制底线；UI Skill 负责任务专属输入、审查步骤、发现分类、输出结构和失败分支；项目上下文负责提供已批准的设计系统；工具适配层只声明真实可用的浏览器、截图、扫描等能力；评测层独立验证行为。
- 必须先识别项目已批准的设计规范与现有组件模式。规范缺失应报告 `MISSING_STANDARD` 并提出候选基线，不得虚构规则。
- 检查现有页面时先审查证据再提出修改；修复遵循最小差异和用户修改保护，重大风格/公共组件变更需要适当批准。
- 静态代码、运行时交互、截图视觉对比、无障碍扫描和人工验收须分别记录证据；任何未执行项不得标记 `PASS`。
- UI 评测基准位于 `examples/evaluation/ui-quality-governance-suite.yaml`，注册表中的初始 `validation_status` 保持 `UNKNOWN`，直至真实工具试点完成。

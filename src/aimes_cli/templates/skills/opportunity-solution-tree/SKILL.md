# Skill: 机会-解决方案树 (Opportunity-Solution Tree)

## Purpose / 目的与价值主张

基于 Teresa Torres 的机会-解决方案树 (Opportunity-Solution Tree, OST) 框架，系统性地探索、验证和优先级排序产品机会。帮助产品团队从客户问题出发，构建结构化的探索路径，基于证据而非假设进行产品决策。

**核心价值**: 
- 将模糊的产品想法转化为结构化的机会空间
- 基于客户问题而非解决方案进行思考
- 提供可视化的探索路径和决策依据
- 支持数据驱动的产品决策

## Input / 输入要求

**最佳输入**: 产品领域、目标客户群体、需要解决的核心问题
**有用补充**: 已有的客户反馈、市场数据、竞品分析、团队假设

**示例调用**: `为面向中小型企业的项目管理 SaaS 产品构建机会-解决方案树，重点关注团队协作效率问题`

## Key Concepts / 核心概念

### 机会-解决方案树框架 (Teresa Torres)

机会-解决方案树是一种可视化工具，帮助产品团队：

1. **定义机会空间**: 从客户角度定义需要解决的问题
2. **探索机会**: 系统性地发现和验证机会
3. **生成解决方案**: 针对机会提出各种可能的解决方案
4. **验证和优先级排序**: 基于证据验证和优先级排序

### 核心组件

#### 1. 机会空间 (Opportunity Space)
- **定义**: 从客户角度描述的需要解决的问题
- **格式**: "当 [情况] 时，[客户] 想要 [目标]"
- **示例**: "当项目复杂度增加时，项目经理想要更好地跟踪团队进度"

#### 2. 机会 (Opportunities)
- **定义**: 解决机会空间的具体途径
- **特征**: 具体、可验证、以客户为中心
- **示例**: "提供实时的项目进度可视化"

#### 3. 解决方案 (Solutions)
- **定义**: 针对机会的具体实现方案
- **特征**: 具体、可执行、可测试
- **示例**: "开发 Kanban 看板功能"

#### 4. 实验 (Experiments)
- **定义**: 验证解决方案有效性的测试
- **特征**: 可测量、快速、低成本
- **示例**: "与 5 个客户进行原型测试"

### OST 与其他框架的关系

| 框架 | 关注点 | 与 OST 的关系 |
|------|--------|---------------|
| 机会-解决方案树 | 机会探索和验证 | 核心框架 |
| 客户旅程映射 | 客户体验流程 | 输入来源 |
| 问题框架画布 | 问题定义和验证 | 补充工具 |
| 精益画布 | 业务模式 | 战略层面 |
| 用户故事映射 | 用户需求组织 | 执行层面 |

### 为什么使用 OST

1. **客户中心**: 从客户问题出发，而非解决方案
2. **结构化**: 提供清晰的思考框架和可视化工具
3. **可验证**: 基于证据进行决策，减少假设
4. **灵活**: 适用于各种产品类型和开发阶段
5. **协作**: 促进团队内部和跨部门的协作

### 反模式 (Anti-Patterns)

1. **解决方案导向**: 从解决方案出发，而不是从客户问题出发
2. **过于宽泛**: 机会空间定义过于宽泛，无法具体执行
3. **缺乏验证**: 基于假设进行决策，不进行验证
4. **静态树**: 树构建后不再更新，无法反映新的见解
5. **忽略数据**: 不基于数据和证据进行优先级排序

## Application / 应用流程

### 第一步: 定义机会空间

从客户角度定义需要解决的问题：

1. **识别客户**: 明确目标客户群体
2. **描述情况**: 描述客户面临的具体情况
3. **明确目标**: 描述客户想要实现的目标

**模板**: "当 [情况] 时，[客户] 想要 [目标]"

**示例**:
- "当项目复杂度增加时，项目经理想要更好地跟踪团队进度"
- "当团队分布式协作时，开发者想要更高效的沟通方式"
- "当产品需求变化时，产品经理想要更快速地适应变化"

### 第二步: 探索机会

系统性地发现和定义机会：

1. **头脑风暴**: 与团队一起 brainstorm 可能的机会
2. **客户访谈**: 通过客户访谈收集真实的痛点
3. **数据分析**: 分析现有数据寻找机会
4. **竞品分析**: 分析竞品产品寻找差异化机会

**机会特征**:
- 具体: 可以明确描述
- 可验证: 可以通过实验验证
- 以客户为中心: 从客户角度出发
- 与业务目标相关: 支持业务目标

### 第三步: 生成解决方案

针对每个机会生成多种可能的解决方案：

1. **头脑风暴**: 针对每个机会 brainstorm 多种解决方案
2. **技术可行性**: 评估解决方案的技术可行性
3. **业务可行性**: 评估解决方案的业务可行性
4. **客户价值**: 评估解决方案为客户带来的价值

**解决方案特征**:
- 具体: 可以明确描述
- 可执行: 可以具体实施
- 可测试: 可以通过实验验证
- 创新: 与现有解决方案有所不同

### 第四步: 优先级排序

基于多个维度对机会和解决方案进行优先级排序：

**评估维度**:
1. **客户价值** (Customer Value): 为客户带来的价值大小
2. **业务价值** (Business Value): 对业务的影响程度
3. **可行性** (Feasibility): 技术和资源的可行性
4. **信心度** (Confidence): 对成功的信心程度
5. **工作量** (Effort): 实施所需的工作量

**排序方法**:
- **RICE**: (Reach × Impact × Confidence) / Effort
- **WSJF**: Cost of Delay / Job Duration
- **加权评分**: 基于多个维度的加权评分

### 第五步: 设计实验

为高优先级的解决方案设计验证实验：

1. **定义假设**: 明确需要验证的假设
2. **选择指标**: 选择可测量的成功指标
3. **设计实验**: 设计低成本、快速的验证实验
4. **执行实验**: 执行实验并收集数据
5. **分析结果**: 分析实验结果，验证或否定假设

**实验类型**:
- 用户访谈: 验证客户需求
- 原型测试: 验证解决方案可用性
- A/B 测试: 验证解决方案效果
- 数据分析: 验证业务影响

## Evidence Labeling System / 证据标签系统

所有分析点必须标注以下标签之一：

- **Fact**: 基于公开可验证的数据、文档或权威来源
  - 示例: 客户访谈记录、市场调研数据、产品使用数据
- **Inference**: 基于逻辑推理、模式识别或专业判断的合理结论
  - 示例: 基于客户行为模式推断需求、基于技术趋势推断机会
- **Assumption**: 基于假设的前提条件，需要进一步验证
  - 示例: 客户会喜欢这个功能、这个解决方案会提高转化率

**标签使用指南**:
- 优先使用 Fact 标签，基于真实数据
- 明确标注 Inference 的推理过程和依据
- 列出需要验证的 Assumption，并设计验证方法

## Common Pitfalls / 常见陷阱

### 陷阱 1: 解决方案导向思维
**表现**: 从解决方案出发，寻找问题来匹配
**解决方案**: 从客户问题出发，探索可能的解决方案
**工具**: 使用"5 个为什么"技术深入理解问题

### 陷阱 2: 过于宽泛的机会空间
**表现**: 机会空间定义过于宽泛，无法具体执行
**解决方案**: 将宽泛的空间分解为具体的机会
**工具**: 使用问题分解技术

### 陷阱 3: 忽视验证
**表现**: 基于假设进行决策，不进行验证
**解决方案**: 设计并执行验证实验
**工具**: 使用实验设计模板

### 陷阱 4: 静态树
**表现**: 树构建后不再更新
**解决方案**: 定期回顾和更新树
**频率**: 每次新的见解或数据，每月正式回顾

### 陷阱 5: 忽略数据
**表现**: 不基于数据和证据进行优先级排序
**解决方案**: 使用结构化的评分方法
**工具**: RICE、WSJF 等优先级框架

### 陷阱 6: 过度复杂化
**表现**: 树过于复杂，难以理解和使用
**解决方案**: 保持树的简洁性，聚焦关键机会
**工具**: 使用 MECE 原则 (Mutually Exclusive, Collectively Exhaustive)
